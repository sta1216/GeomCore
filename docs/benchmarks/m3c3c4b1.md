# M3c-3c-4b1 benchmark note

## Scope

M3c-3c-4b1 makes the synthetic-domain splitter usable on a cone lateral face: the
apex is projected onto the chart, `trim_face_domain` describes the cone chart,
`split_face_curved` dispatches a canonical cone face to `trim_face_split_domain`, and
an open cut may end on any domain side. It adds no benchmark executable and no timing
gate: the acceptance oracles are the exact uv areas, the apex-row counts, the apex
evaluation, bitwise determinism, and the pinned refusals. This note records only the
numbers measured for this milestone.

## Environment

- MSVC 19.44 (Visual Studio 17 2022), Windows x64.
- CMake 4.4.4; `GEOM_WERROR=ON`, `/W4 /WX /utf-8`; zero warnings in Debug and Release.
- Cone fixture tolerance `1e-12`; split tolerance `1e-9`.

## Fixture

Canonical cone at the origin: `make_cone({0,0,0}, {0,0,1}, 1, 2, 1e-12)`. Its lateral
face is cut along `u = 0`, so the chart is `[0, 2*pi] x [0, 2]` with `v = 0` the base
rim and `v = 2` the collapsed apex. A meridian from `(0.7, 0)` to `(0.7, 2)` is
deliberately not one of the `pi/32` side samples, so the splitter must split the base
side segment at the open end.

The exact uv partitions are `0.7` for the wedge between the seam and the cut, and
`2*(2*pi - 0.7) = 11.166370614359172` for the wide remainder. The narrow wedge carries
one apex-row point at the cut end; the wide remainder carries the cut end and the
back-seam copy at `u = 2*pi`, so two apex-row points. Both evaluate to `(0,0,2)`.

## QA case

`QA-21: a cone meridian split is deterministic and closes at the apex`
(`tests/unit/brep_trim_face_test.cpp`) calls the public
`split_face_curved(cone, lateral, {{(0.7,0),(0.7,2)}}, 1e-9)` and asserts:

| quantity | measured | gate |
| --- | ---: | --- |
| fragments | 2 | exactly 2 |
| uv area, narrow wedge | `0.7` | `1e-9` relative |
| uv area, wide remainder | `11.166370614359172` | `1e-9` relative |
| apex-row points | 1 / 2 | exact counts |
| apex evaluation | `(0,0,2)` | every `v == 2` point within `1e-12` |
| second run | bitwise equal | every uv and 3D coordinate |
| focused run | 1 case / 32 assertions / 0 failed | exit 0 |

It intentionally repeats the Task 3 meridian acceptance as the end-to-end pin and adds
no new behaviour.

- Full suites: Debug 1001 cases / 670,383 assertions / 0 failed, exit 0; Release 1001
  cases / 670,383 assertions / 0 failed, exit 0.
- QA-21 adds 1 case / 32 assertions over the 1000 / 670,351 baseline. The baseline
  already contains the Task 2 closed-cut case (`pi` cap with one apex, `2*pi` band
  with none) and the Task 3 generic-rectangle open cut.

## No boolean operation

No boolean operation is enabled or changed. The gate is still
`boolean_solid_curved: cone operands need closed-cut and apex topology; booleans are
deferred to M3c-3` (`include/geom/brep/boolean_solid_curved.hpp:187`), pinned by the
existing cone rejection tests in `tests/unit/brep_boolean_curved_test.cpp`. This
milestone splits a face in isolation; it does not run, feed, or measure a boolean.

## Refusals pinned

| input | result |
| --- | --- |
| meridian ending at `(0.7, 1)` inside the chart | `trim_face: cut chain ends inside the parameter domain` |
| cut chain lying on a domain side | `split_face_curved: cut lies on the parameter domain boundary` |
| open piece leaving through a seam and returning elsewhere | `split_face_curved: open cut crosses the seam` |
| trimmed cone face (stored loop not the full half-chart) | `split_face_curved: trimmed cone faces are not supported yet`, context `(face.index(), 0)` |
| cone volume | `curved_solid_volume: cone faces are not supported yet` |
| cone trimmed boundaries | `trimmed_face_boundaries: cone faces are not supported yet` |
| cone boolean operands | the gate message above |

## Deferred

`assemble_curved_solid` / `assemble_solid` fail on the two halves with `edge is used
once`, and the collapsed side would add a zero-length apex edge. Cone booleans stay
behind the gate; trimmed cone faces, cone volume and cone trimmed boundaries keep
their refusals; trimmed-cone tessellation and apex-fan volume are deferred because a
split fragment's apex row does not match `tessellate_cone_face`'s whole-ring fan.
